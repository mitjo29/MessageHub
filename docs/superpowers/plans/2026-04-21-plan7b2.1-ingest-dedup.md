# Plan 7b.2.1: Ingest Dedup + Adapter Cursor Persistence — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make ingest idempotent so a `RawMessage` with the same `(channel, external_id)` tuple ingested N times results in exactly one row — and make the Telegram adapter's `last_update_id` cursor survive restarts, so `getUpdates` actually advances.

**Architecture:** Two reinforcing fixes. First: add `messages.external_id TEXT NULL` + a partial unique index on `(channel_type, external_id) WHERE external_id IS NOT NULL`. `Store::insert_message` uses `INSERT … ON CONFLICT DO NOTHING`, so the constraint catches any future writers (reply composer, mobile sync) automatically. Second: extend the `ChannelAdapter` trait with `cursor_state()` / `set_cursor_state()`. The `channels.last_sync_cursor` column already exists and `Store::update_sync_state` already takes a cursor — nothing downstream changes, we just stop passing `None`. Telegram uses it to persist `last_update_id`; Email is a no-op for now (since-based IMAP is good enough once dedup exists).

**Tech Stack:** Rust 1.75+, rusqlite / SQLCipher. No new deps.

**Prerequisites:**
- Master at `ed6209b` or later (Plan 7b.2 merged, runtime-demo DB-path fix in place).
- `cargo build --workspace` clean on a fresh checkout.
- The manual verification of 7b.2 (checks #1–10, #13, #14) already passed — this plan fixes what blocked #11 and #12.

**Spec:** (This plan is the spec. B-003 in `docs/backlog.md` is the one-paragraph version.)

---

## Invariant

After this plan: **for any `(channel, external_id)` where `external_id.is_some()`, the `messages` table contains at most one row.** Messages with `external_id = None` are exempt (the `WHERE external_id IS NOT NULL` clause on the unique index).

This holds even if the ingestor is called with the same `RawMessage` a thousand times, across process restarts, across adapter reconnects.

`★ Why this matters:` This is the glue. On startup, the channel task loads `config.last_sync_cursor` and hands it to the adapter via `set_cursor_state`. - [ ] **Step 2: Persist cursor after each successful batch**

In the same file, find the arm that handles a successful fetch — around:

```rust
Ok(batch) => {
    let count = batch.len();
    let latest_ts = batch.iter().map(|m| m.timestamp).max();
    // ... ingest_tx.send ...
    if let Some(ts) = latest_ts {
        {
            let guard = store.lock().expect(...);
            if let Err(e) = guard.update_sync_state(&channel_id, None, ts) {
                ...
            }
        }
        last_sync_at = Some(ts);
    }
}
```

Replace the `update_sync_state(&channel_id, None, ts)` call to pass the adapter's current cursor. Because `adapter.cursor_state().await` is async, do the `.await` outside the lock (same rule as `fetch_messages`):

```rust
// Capture the adapter's current cursor BEFORE we grab the store
// lock — cursor_state is async and we never hold the lock across await.
let cursor_after = adapter.cursor_state().await;

if let Some(ts) = latest_ts {
    {
        let guard = store.lock().expect("channel_task: store mutex poisoned");
        if let Err(e) = guard.update_sync_state(&channel_id, cursor_after.as_deref(), ts) {
            warn!(%channel_id, error = %e, "channel task: failed to persist cursor");
        }
    } // lock released here
    last_sync_at = Some(ts);
}
```

## Notes for the executor

- **Schema compatibility:** Existing rows get `external_id = NULL` after the `ALTER TABLE`. The partial index explicitly skips them, so no legacy row can collide with a newly-ingested one. Nothing needs to be backfilled.
- **First-write-wins is intentional.** `ON CONFLICT DO NOTHING` keeps the original row and silently discards subsequent inserts. If an adapter ever needs to update a message (edit-in-place from Telegram, for example), that's a *different* fix — use `INSERT ... ON CONFLICT DO UPDATE` explicitly and name the fields to update. Out of scope for B-003.
- **Don't try to fix email's `since` watermark here.** IMAP's `SINCE` is date-granular and re-delivers messages on the boundary; the dedup layer catches those. Tightening the watermark is a follow-up, not a blocker.
- **Do not add a "mark duplicated, link to original" mechanism.** YAGNI — the frontend doesn't need to know dups happened.
- **If `fetch_messages` signature change breaks a caller you didn't expect:** the runtime factory likely wraps the adapter in `Box<dyn ChannelAdapter>`. Dispatch through a `&mut` reference — same code, just `&mut *adapter` where needed.
